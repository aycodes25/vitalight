# Vitalight Pharmacy

A responsive pharmacy storefront built with React, Vite, and an Express API. Product cards and prices in `shared/catalog.js` are starter catalogue content for the storefront; update them to match your actual stock before accepting orders.

## Run locally

1. Install Node.js `>=22.22.2 <23` or `>=24.15.0` (required by the installed test tooling, jsdom 30 and Vitest 5) and npm.
2. Run `npm install`.
3. Copy `.env.example` to `.env`. Set the Supabase project URL in `VITE_SUPABASE_URL` and `SUPABASE_URL`, and its publishable/anon key in `VITE_SUPABASE_ANON_KEY`. Set the **server-only** `SUPABASE_SERVICE_ROLE_KEY` and add one or more invited, email-confirmed administrator accounts to the comma-separated `ADMIN_EMAILS` entry.
4. In the Supabase SQL editor of a **new** project run, in order: `supabase/schema.sql`, `supabase/migrations/001_catalogue_v2.sql` and, only if you want the sample catalogue, `supabase/migrations/002_seed_catalogue.sql`. This creates the tables, the 12 categories, the `product-images` bucket and (with 002) 120 sample products in total. The sample catalogue is placeholder content: review names, prices and stock before taking orders. Existing live databases follow the runbook below instead.
5. Optional: set `VITE_PHARMACY_PHONE`, `VITE_PHARMACY_WHATSAPP` and `VITE_PHARMACY_EMAIL` in `.env` so the storefront shows contact buttons.
6. In Supabase Authentication, invite your admin email address and confirm that it matches an entry in `ADMIN_EMAILS`.
7. Run `npm run dev` and open the Vite URL printed in the terminal. The admin area is at `/admin`.

The Express API runs on port 3001 in development. `npm run build` creates the production storefront, and `npm start` serves the built app and API together. Vite's development server exposes only the `/api` proxy to Express. Set `PORT` to change the server port.

## Project layout

- `frontend/` – customer site (Vite + React, `npm run dev`)
- `shared/` – logic, catalogue data and product artwork used by both client and server
- `backend/` – Express API (`createApp` in `backend/app.js`)
- `supabase/` – schema and migrations (`002_seed_catalogue.sql` is generated by `node scripts/generate-seed.js` from `shared/catalog.js`)

Run `npm test` for the unit tests. Production: `npm run build` then `npm start`.

## Supabase and order requests

The `/admin` workspace includes a summary dashboard, searchable product catalogue, image uploads, pricing and stock controls, featured/visibility controls, category management, and customer order review and status updates. Admin API routes verify Supabase Auth access tokens on the server and check the verified account email against `ADMIN_EMAILS`; they are not protected only by hiding the page. Create/invite admin accounts through Supabase Auth—there is no public admin signup.

The service-role key is used only by the Express server and must never be added to client-side code or committed. Product, category, and order tables have row-level security enabled with no public policies; privileged database operations go through the verified server API. Product photos are restricted to JPEG, PNG, and WebP up to 5 MB and uploaded to the public `product-images` bucket. Do not upload private or patient information.

Until Supabase and an admin account are configured, the storefront remains browsable using starter catalogue data, while the admin login and order submissions explain which setup is missing. Starter catalogue content and prices in `shared/catalog.js` and `supabase/schema.sql` are examples; replace them with verified stock and pharmacy prices before taking orders. Orders are requests only—not payments. The pharmacy should confirm availability, final price, delivery, and any prescription requirements directly with the customer before fulfilment.

## WhatsApp customer care and order forwarding

The customer-care number is set with `VITE_PHARMACY_WHATSAPP` (default `2348105079027`, i.e. 08105079027; local `0...` numbers are converted to `234...`).

- A floating chat button on every page opens a WhatsApp chat with customer care (hidden if no number is set).
- After a customer sends an order request, the success screen offers **Send order on WhatsApp**, which opens WhatsApp with the order details pre-filled.

Honest note: the order is saved in the admin AND the customer sends the pre-filled WhatsApp message with one tap. Fully automatic server-to-WhatsApp forwarding needs the WhatsApp Business Cloud API (Meta business account, access token, approved templates) and is not included.

## Deploy runbook for an existing live database

Follow these steps in order when this version replaces one that is already live.

1. **Before deploying**, apply `supabase/migrations/001_catalogue_v2.sql` in the Supabase SQL editor. It adds the `brand`, `rx_required` and `sort_order` columns and the 12 categories that this version reads. The previous version keeps working with these additions.
2. Also apply `supabase/migrations/003_product_images.sql` (adds the `images` photo gallery column). Apply it together with 001, before deploying. If it is missing the storefront keeps working with each product's main photo, but saving several photos in the admin needs it.
3. **Deploy** this version.
4. **Review and trim the catalogue** in `/admin`: check names, prices, stock and visibility of your real products.
5. Apply `supabase/migrations/002_seed_catalogue.sql` **only if** you want the 113 sample products published. They are created with `is_active = true` and sample prices and stock, so they appear on the live storefront immediately. Delete or edit them in the admin before taking orders.

If you skip `002_seed_catalogue.sql` on an existing database, review the tags and descriptions of the 7 original products in the admin, as older versions used promotional wording there.

Re-running `supabase/schema.sql` re-creates 4 empty legacy categories. Re-run `001_catalogue_v2.sql` afterwards to remove them.

## Real product photos

The storefront shows a product's `image_url` photo instead of the illustration whenever one is set. To attach your own photos in bulk:

1. Take square photos (JPEG, PNG or WebP, up to 5 MB each) and name each file after the product id, for example `paracetamol-500mg.jpg`. Find product ids in the admin product list or in `shared/catalog.js` (the first value of each product row).
2. Put the files in a folder, for example `./photos`, and make sure `.env` has `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY`.
3. Preview the matches: `npm run images -- ./photos --dry-run`. Nothing is uploaded; the table lists matched, unmatched and invalid files.
4. Upload for real: `npm run images -- ./photos`.

Photos replace the illustration automatically. You can also upload a photo for a single product from the admin product form. Do not include private or patient information in photos.

## Multiple product photos

Each product can have up to 8 photos. In the admin product form, choose several JPEG, PNG or WebP files at once (5 MB each). New photos are listed with a preview; use **Make main** to move a photo to the front and **Remove** to drop one. The first photo is the main photo: it is stored as `image_url` and shown on product cards, while the product page shows the full gallery with thumbnails. Photos upload one by one after the product is saved; if one fails, the product and the other photos are kept and the failed files are listed so you can save again to retry.

Galleries need `supabase/migrations/003_product_images.sql` (the `products.images` column). Without it the app keeps working with a single main photo: the admin accepts one new photo per save and it replaces the main photo (extra files are rejected with a message), and the storefront shows each product's `image_url`. Apply 003 to unlock the full gallery.

The `npm run images` CLI is safe to re-run: photos are stored under a name derived from the file contents (`<product-id>/<sha1>.<ext>`), so the same folder gives the same URLs and never adds duplicates. The new photo goes first and earlier photos follow (up to 8; the summary reports how many older photos were dropped). Without the column it only sets `image_url`.

## Troubleshooting

- **Storefront shows the sample catalogue banner and `/api/catalog` returns 503.** The live Supabase database is missing `supabase/migrations/001_catalogue_v2.sql`. The API selects the new columns `brand`, `rx_required` and `sort_order`; until they exist the query fails, the API answers 503 and the storefront falls back to the bundled sample catalogue. Apply the migration (see the runbook above).

## Making the site look real: your own photos

**Hero photo (home page).** Save a landscape photo of your pharmacy (about 1200 x 900, JPEG) as `frontend/public/hero.jpg`, then run `npm run build`. The home page shows it instead of the illustrations. If the file is missing, the illustrations stay.

**Product photos.**
1. `npm run images:list` writes `photos-checklist.csv`: every active product, the exact filename its photo needs, and whether it already has one.
2. Put the photos in a folder (for example `photos/`) named exactly as in the `filename` column.
3. `npm run images -- ./photos --dry-run` shows what would be attached; run it again without `--dry-run` to upload.

Good sources are photos you take yourself, or the product image packs that manufacturers and distributors usually give registered pharmacies for free. Do not copy photos from other websites or search results without permission, and make sure each photo shows the product (brand and strength) you actually sell.
